## 13:58 · 命令预览升级为「能力级预计」（替换当日早先的纯文案方案）

- 现象：抽屉把扫描后的命令标为「plan」且无提示，读起来像可执行的真实命令；
  实际它由 `buildPreviewHwPlan()` 用 **CPU 层模板** 合成，在任何有硬件编码器的机器上都是错的。
- 根因：分层决策本就分两层——第一层 `resolveTiers({caps,decodeMode,hwaccel})` 只依赖硬件能力、
  不碰文件；第二层 `selectTier` 才逐层 `probeLayer` 干跑 ffmpeg。旧预览直接跳过第一层、写死 cpu。
- 改动（引擎）：`core/transcode/hwaccel.js` 新增 `resolvePreviewHwPlan()`——取候选链首层，
  **复用执行期同一套 `gpuBlocksDecode` GPU 矩阵预筛**，音频文件/音频预设与 `resolveHwPlan`
  同口径回落 cpu，`caps` 缺失或 `resolveTiers` 抛错时一律回落 cpu（绝不抛错，
  否则会让 `createPlan` 整体失败）。经 `core/transcode/index.js` facade 暴露。
- 改动（主进程）：`FfmpegEnvironment.buildPreviewHwPlan(opts)` 改为委托该引擎函数，
  由 `ffmpeg-service.createPlan` 传入首任务的 codec/像素格式/位深与 `decodeMode/hwaccel`。
- 改动（文案）：命令卡标注由「示意」改为「**预计**」，黄条说明「按本机能力推断、
  未逐文件干跑；该文件解不开或失败重试时可能降级」。`estimate`（未扫描）态措辞同步。
- 边界：**不做** `probeLayer` 干跑（扫描期不跑 ffmpeg）；个别文件的真实降级无法静态预判。
- 真机实证（RTX 4070 / ffmpeg 8.1.2）：预览由 `libx264|libx265` 变为
  `-hwaccel cuda -hwaccel_output_format cuda … -c:v h264_nvenc|hevc_nvenc`；10bit HEVC 与
  音频（→cpu 占位）两条分支符合预期。

### 追加 · 编码侧 AV1 预筛（仅预览）

- 背景：`NVENC_MATRIX` 有意不参与 `selectTier` 预筛（缩放链路已把 4:2:2/4:4:4 转 4:2:0，
  NVENC 色度限制不触发，见 `core/transcode/gpu.js` 注释）。唯一不会被化解的是
  **AV1 编码仅 Ada(40 系) 起支持**：预 Ada 的 N 卡跑 av1 预设时，cuda/swdec/d3d 三层的
  `av1_nvenc` 都会在真实执行期探测失败并降级，而 `caps.encoders`（构建级）拦不住。
- 改动：`hwaccel.js` 新增私有 `nvencEncodeBlocked()`（与 `buildVideoArgsFromPlan` 同源解析
  该层编码器：swdec 走厂商行，其余走 `ENCODER_MATRIX`），在 `resolvePreviewHwPlan` 的候选
  循环里跳过「用 `*_nvenc` 且本代次不支持目标编码族」的层；`codecFamily` 由宿主经
  `codecFamilyOfPreset(activePreset)` 传入（facade 新增该导出）。
- 边界：**只影响预览**，`selectTier` 与执行行为不变；无 `gpuProbe.generation` 时不启用（不误伤）；
  h264/hevc 的 yuv420p 全代次 yes，不会命中。
- 新增单测 4 例（Ampere+av1→cpu、Ada+av1→cuda、h264/hevc 不受影响、无代次不启用）。
- 真机回归（RTX 4070/Ada，`F:\Temp\testvideos` 样本）：h264 4:2:2（8/10bit）正确落到
  `swdec`（解码矩阵 ONLY50 命中）；hevc 444-10bit 与 av1 源均 `cuda`；av1 预设在这台 Ada 上
  仍为 `cuda/av1_nvenc`（未误伤）。
- **已知残留（本次未动，非本改动引入）**：`vvc` 与 `vp9 444` 不在 NVDEC 矩阵覆盖范围
  （前者无矩阵数据、后者仅有 420 键），预览会高估为硬件层，真实执行探测失败后才降级。
  `selectTier` 行为本就如此，预览只是如实反映「能力级推断」。

    ① loglevel（`log.info/warn/error/debug`，经插件）；② `logWithTag` 家族
    （`logInfo/logWarn/logError/logSuccess/logTask/…`，绕过 loglevel 直接 console.log）。
    汇聚文本用原始参数（不经 chalk 着色、对象走 `util.inspect`），并按实测剥离
    loglevel-plugin-prefix 拼接进首参的 `<级别> ` 前缀。

    `registerLogSink()` 转发（保持对 `core/` 的 import 仍只在 ffmpeg-service.ts）；
    `main/index.ts` 注册桥接：仅转发 INFO/WARN/ERROR（DEBUG/TRACE 会淹没面板），
    窗口未加载完成时跳过，转发为既有的 `task.log` 引擎事件 → 渲染层零改动。
- 真机/自动化验证：临时脚本确认两条路径均被汇聚（含 `level/tag/message` 字段与前缀剥离）；
  新增 e2e 断言「打开日志抽屉能看到 `[hwdetect]` 初始化日志」。
- 遗留（本次未修，见下条审计）：引擎 `log.info/debug` 受 loglevel 默认级别 WARN 过滤、
  引擎 INFO 日志不落文件、面板日志不持久化等。

## 18:23 · 硬件设备探测失败原因入日志（排查 QSV 不可用）

- 起因：本机 QSV 被判不可用（`usable.qsv=false`）。排查结论：**非显卡/驱动/环境问题**——
  QSVEncC 可正常枚举 `Intel UHD Graphics 750`（Media SDK 2.16 / Hardware API 2.15），
  且同一条探测命令在 `ff8`/`ff9`/`nomercy-ffmpeg-9` 上 `exit=0`，只有 PATH 里那个
  **shared 变体**（7 个 avcodec/avutil DLL）失败：设备级 MFX 会话能建立（oneVPL 2.16/impl 2.15），
  但**编码器自建会话**返回 `-9`（`MFX_ERR_DEVICE_FAILED`）。已由用户替换该构建，现 `usable.qsv=true`。
- 问题：`probeDeviceUsable` 只返回布尔，`probeDetail` 恒为 `"device init failed"`，
  看不出是驱动、构建还是设备缺失；且该字段未进任何 INFO 日志，实际不可见。
- 改动（`core/transcode/hwdetect.js`，**不改判定逻辑**）：
  - `probeDeviceUsable` 改为返回 `{ ok, reason }`，失败时用新增的 `probeFailureReason()`
    从 stderr 取一条可读原因（优先含 error/failed 的行，剥掉 `[模块 @ 地址]` 前缀，截断 240 字符），
    超时与异常路径也带回原因；四个调用点（cuda/qsv/amf/d3d）据此写 `probeDetail`。
  - `logEnvironment()` 新增一行 INFO：`device probe failed (usable=false): qsv: ... | amf: ...`
    （只列「静态具备、实际探测过且失败」的层）。
- 真机验证：替换后的 bin → `usable.qsv=true`、`probeDetail.qsv="device ok"`；
  以 `ff7` 构造失败路径 → `qsv: device init failed: Error initializing an MFX session: -3.`；
  无 A 卡的 AMF 仍如实记为 `DLL/device unavailable (e.g. amfrt64.dll): DLL amfrt64.dll failed to open`。

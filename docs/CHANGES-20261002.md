## 13:58 · 命令预览升级为「能力级预计」（替换当日早先的纯文案方案）

- 现象：抽屉把扫描后的命令标为「plan」且无提示，读起来像可执行的真实命令；
  实际它由 `buildPreviewHwPlan()` 用 **CPU 层模板** 合成，在任何有硬件编码器的机器上都是错的。
- 根因：分层决策本就分两层——第一层 `resolveTiers({caps,decodeMode,hwaccel})` 只依赖硬件能力、
  不碰文件；第二层 `selectTier` 才逐层 `probeLayer` 干跑 ffmpeg。旧预览直接跳过第一层、写死 cpu。
- 改动（引擎）：`core/transcode/hwaccel.js` 新增 `resolvePreviewHwPlan()`——取候选链首层，
  **复用执行期同一套 `gpuBlocksDecode` GPU 矩阵预筛**，音频文件/音频预设与 `resolveHwPlan`
  同口径回落 cpu，`caps` 缺失或 `resolveTiers` 抛错时一律回落 cpu（绝不抛错，
  否则会让 `createPlan` 整体失败）。经 `core/transcode/index.js` facade 暴露。
- 改动（主进程）：`FfmpegEnvironment.buildPreviewHwPlan(opts)` 改为委托该引擎函数，
  由 `ffmpeg-service.createPlan` 传入首任务的 codec/像素格式/位深与 `decodeMode/hwaccel`。
- 改动（文案）：命令卡标注由「示意」改为「**预计**」，黄条说明「按本机能力推断、
  未逐文件干跑；该文件解不开或失败重试时可能降级」。`estimate`（未扫描）态措辞同步。
- 边界：**不做** `probeLayer` 干跑（扫描期不跑 ffmpeg）；个别文件的真实降级无法静态预判。
- 真机实证（RTX 4070 / ffmpeg 8.1.2）：预览由 `libx264|libx265` 变为
  `-hwaccel cuda -hwaccel_output_format cuda … -c:v h264_nvenc|hevc_nvenc`；10bit HEVC 与
  音频（→cpu 占位）两条分支符合预期。
